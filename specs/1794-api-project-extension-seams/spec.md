# Feature Specification: API project extension seams

**Issue**: #1794  **Status**: Draft  **Areas**: none (no `area:*` label matches the API backend; see Assumptions)

## User Scenarios and Testing

### User Story 1 - Add a complete API feature without editing template files (Priority: P1)

A derived-project developer adds a new capability consisting of an HTTP endpoint, a persistent data model, a configuration value, an event subscription, a background job, and a permission, placing all new content inside the designated project extension area. The endpoint serves traffic, the model is picked up by migration autogeneration, and the permission can be assigned and is enforced by the server — with zero modifications to template-owned content.

**Independent test**: Create the demo feature using only the project extension area, then verify the endpoint responds, a migration is autogenerated for the model, and a caller with the new permission is authorized while one without it is denied.

**Acceptance scenarios**:
1. Given a derived project with only extension-area content added, When the API starts, Then the new endpoint is served and the new event subscription and job are active.
2. Given the demo model exists only in the extension area, When migration autogeneration runs, Then a migration covering the new table is produced.
3. Given the new permission granted to a caller, When the protected endpoint is called, Then access is allowed; Given the permission absent, Then access is denied.

### User Story 2 - Template behavior is unchanged when no extensions exist (Priority: P1)

A template maintainer or adopter who adds no project extensions gets exactly the current behavior: the same endpoints, the same event subscriptions, the same jobs, and the same permission set, with startup succeeding on the default configuration.

**Independent test**: Run the API and the existing test suite with an empty (or default) project extension area and confirm no behavior, subscription, or permission differences versus the unmodified template.

**Acceptance scenarios**:
1. Given no project extensions, When the API starts, Then all template event subscriptions are registered and active.
2. Given no project extensions, When the permission catalog is queried, Then it contains exactly the template permission set.

### User Story 3 - A failing or empty extension cannot silently break the template (Priority: P2)

An operator can tell when project extension loading is misconfigured instead of silently running with missing routes, jobs, subscriptions, or permissions.

**Independent test**: Configure a nonexistent or broken extension and start the API; observe a loud, diagnosable failure rather than silent startup with missing capabilities. [NEEDS CLARIFICATION: fail-fast vs. skip-and-log on extension load failure]

**Acceptance scenarios**:
1. Given an extension that fails to load, When the API starts, Then the outcome is the documented failure behavior (loud failure, not silent partial startup). [NEEDS CLARIFICATION: exact failure behavior]

## Requirements

- **FR-001**: The system MUST let a derived project contribute HTTP endpoints that are served by the API without modifying template-owned content.
- **FR-002**: The system MUST discover data models defined in the project extension area so that migration autogeneration includes them without modifying template-owned content.
- **FR-003**: The system MUST let a derived project define its own configuration values without editing template-owned configuration.
- **FR-004**: The system MUST let a derived project subscribe to platform events, receiving access to the existing event registry and message bus alongside template subscriptions, which MUST continue to be registered.
- **FR-005**: The system MUST let a derived project register background jobs on the shared job registry without modifying template-owned content.
- **FR-006**: The system MUST accept project-defined permission strings so they can be assigned (e.g. to roles or keys) and enforced by server-side authorization.
- **FR-007**: The system MUST drive extension loading from configuration with a safe default, so the API starts and behaves as today when no extensions are present.
- **FR-008**: Template-owned loading content MUST change exactly once to introduce the extension mechanism; adding further features afterwards MUST NOT require template-owned edits.
- **FR-009**: The backend test suite and the migration-consistency check MUST pass with the demo extension feature present, whether the demo is kept as the canonical example or removed before merge. [NEEDS CLARIFICATION: demo kept as canonical example vs. removed]
- **FR-010**: The change MUST carry one adopter-facing release-note line describing the new extension capability and anything adopters must do.

## Acceptance Criteria

- **AC-1**: A demo feature (endpoint plus model plus configuration value plus event subscription plus job plus permission) added using only the project extension area is served, appears in autogenerated migrations, and authorizes correctly, with zero edits to template-owned content (covers FR-001, FR-002, FR-003, FR-004, FR-005, FR-006).
- **AC-2**: Template-owned loading content changes exactly once to introduce the mechanism; no per-feature template edit is needed afterwards (covers FR-008).
- **AC-3**: Template event subscriptions are still registered when a project subscription is present, and the project subscription receives the existing event registry and message bus (covers FR-004).
- **AC-4**: The backend test suite and the migration-consistency check pass with the demo feature present, and the demo's final disposition (kept as canonical example or removed) matches the reviewer's decision (covers FR-009). [NEEDS CLARIFICATION: demo kept vs. removed]
- **AC-5**: The change carries exactly one release-note line per the admission gate for release notes (covers FR-010).
- **AC-6**: With no project extensions, startup succeeds on the default configuration with template behavior unchanged (covers FR-007, FR-004).

## Edge Cases

- Extension area is empty or absent: startup succeeds with template behavior unchanged.
- Extension load failure (missing module, import error, exception during registration): behavior MUST be loud and diagnosable, never a silent partial startup. [NEEDS CLARIFICATION: fail-fast vs. skip-and-log]
- Name collision between a project-defined endpoint, job key, or permission and a template-owned one: the documented precedence or rejection applies (plan stage to define; template behavior MUST NOT be silently overridden).
- Migration autogeneration with both template and project models: a single consistent migration history results (no multiple heads).
- Project-defined permission assigned to a role, then the extension is removed: existing grants degrade to denied access, never to open access.

## Out of Scope

- Web-side (frontend) extension mechanisms — covered by the sibling web-seams item.
- A plugin marketplace, versioning of extensions, or hot-reloading of extensions at runtime.
- Update-flow tooling for derived projects (parent epic); this item only provides the seams that tooling relies on.
- Changes to the template permission catalog itself or to existing authorization semantics.
